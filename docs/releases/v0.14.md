# Soar 0.14

## 0.14.1

Soar 0.14.1 downloads large files over several connections at once, trusts the
certificates your system trusts, and keeps a floating forge declaration in
`packages.toml` as you wrote it.

### Faster Downloads

When a server supports byte ranges, sends a strong ETag, and the file is at
least 8 MiB, Soar splits it into chunks and fetches them in parallel, each over its own connection. This
applies to package installs and to `soar download`. A server that caps each
connection no longer caps the whole download, and a slow connection only holds
up the chunk it is working on while the others carry on.

Soar opens 8 connections by default. Set `download_concurrency` in the config to
change that everywhere, or pass `--connections` to a single download:

```sh
soar download --connections 4 https://example.com/large.iso
soar download --connections 1 https://example.com/large.iso   # one stream
```

An interrupted download resumes chunk by chunk, fetching only what is missing.
A server that does not support ranges, or one that stops honoring them part way,
is downloaded as a single stream, as before.

### Certificates From the System Trust Store

HTTPS requests now verify certificates against the operating system's trust
store rather than a list built into Soar. A certificate authority installed on
the machine, such as a corporate proxy's, is accepted without turning
verification off. Hostname, expiry and chain checks are unchanged.

### Floating Forge Versions Stay Floating

A forge package declared with no version, or with `version = "*"`, is left that
way in `packages.toml`:

```toml
[packages]
gh = { github = "cli/cli", asset_pattern = "gh_*_linux_amd64.tar.gz" }
```

`soar apply` installs the newest release and records it in the local database
only. Once installed, the package is in sync for as long as its release still
matches the declared repository, `asset_pattern` and `tag_pattern`, so a later
`soar apply` makes no request to the forge. `soar update` moves it to the newest
release. A declaration that names a version behaves as before, including having
the new version written back by `soar update`.

### Bug Fixes

- An onelf package that ships a desktop entry for each of its commands gets all
  of them, not only the default command's. A GUI entry launches the GUI command
  rather than the package's default one
- Desktop integration works for onelf packages built by current onelf releases,
  which failed the manifest checksum and were installed without a desktop entry
  or icon
- A package that ships symlinks no longer prints a warning for each one when it
  is installed

## 0.14.0

Soar 0.14.0 adds Codeberg, Gitea and Forgejo as release sources, can integrate
a file without copying it, and hardens how Soar handles the files, links and
downloads it works with.

### Breaking Changes

**System mode reads only `SOAR_SYSTEM_*` variables.** With `--system`, Soar
reads `SOAR_SYSTEM_ROOT`, `SOAR_SYSTEM_BIN` and the other prefixed path
variables, and ignores the unprefixed ones. An exported `SOAR_ROOT` meant for
your own tree no longer redirects the system tree into your home. If you set
paths for system mode through the unprefixed variables, rename them. See
[Environment Variables](../cli-reference.md#environment-variables) for the full
list.

**`soar log` and `soar inspect` are removed.** They only showed a package's
build log and build script, and no repository publishes either anymore. Use
[`soar query`](../inspection.md) to look at a package.

**The metadata database drops the build log fields.** A migration removes the
`build_log` and `build_script` columns the first time a repository's metadata
is used. Metadata that still carries those keys is accepted and the keys are
ignored. An older Soar cannot search a migrated repository and fails with
`no such column: packages.build_script` until the repository publishes new
metadata, or until the metadata database is deleted and synced again.

### Codeberg, Gitea and Forgejo

Releases on Codeberg, and on any Gitea or Forgejo instance, can be downloaded,
declared in `packages.toml`, and updated like GitHub and GitLab releases. An
instance has no fixed host, so it is named by the repository URL:

```sh
soar download --codeberg owner/repo
soar download --gitea https://git.example.com/owner/repo@v1.0.0
```

```toml
[packages]
cb-tool = { codeberg = "owner/repo", asset_pattern = "*x86_64*.AppImage" }
gt-tool = { gitea = "https://git.example.com/owner/repo", asset_pattern = "*x86_64*" }
```

Codeberg reads `CODEBERG_TOKEN`. A Gitea or Forgejo instance is only sent a
token you name for it under
[`forge_tokens`](../configuration.md#forge-rate-limits).

### Integrating a File in Place

`--integrate` links a file you already have into the bin directory without
copying it. An AppImage or onelf binary also gets the desktop entry and icon it
ships:

```sh
soar add ~/Applications/myapp.AppImage --integrate
```

The file is listed and removed like any other package. `soar remove` takes away
the links, desktop entry and icon and leaves the file alone. `soar update` does
not touch it.

### Bug Fixes

- A program shipped beside a package with no published hash is not installed,
  rather than being made executable and possibly linked into `bin`
- An install with no checksum to verify warns that only the connection vouches
  for what was downloaded, and warns more strongly over plain http
- A `provides` entry naming a file the package does not hold is skipped, rather
  than leaving a dead command in `bin` or replacing another package's command
- Soar never replaces a file or link in `bin`, or a desktop entry or icon, that
  it does not own, and removal never touches anything outside the packages
  directory
- A sync builds new metadata beside the old and swaps it in, so a failed sync
  keeps the repository's previous metadata. One repository failing no longer
  stops the others from syncing
- Importing a repository whose packages list several maintainers no longer fails
  with `FOREIGN KEY constraint failed`
- A download that receives nothing for 120 seconds fails instead of hanging, and
  a resumed download that no longer matches the server starts over
- `soar download -o -` writes its logs to stderr, so the output holds only the
  file. `soar download` with several links runs all of them and reports how many
  failed
- The `--ask` prompt accepts `yes` as well as Enter. A closed stdin is an error
  rather than a yes
- Package names read from stdin with `-` can no longer be taken as flags such as
  `--system`
- `soar search --case-sensitive` treats `_` and `%` as literal characters
- `soar use` lists only finished installs and switches to exactly the variant
  you picked
- `soar clean --broken-symlinks` removes only links whose target is gone, not
  ones whose target is merely unreadable
- A required sandbox fails rather than running unconfined where Landlock cannot
  enforce it. Sandboxed commands work with piped input and output, and can read
  the Nix store
- A failed AppImage or onelf integration is reported as a warning rather than
  passed over silently, and onelf files are read within bounds checked against
  the file's real size
- A failed host lookup names the host
